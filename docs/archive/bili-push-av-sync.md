# B 站推流音画不同步：问题与解决方案

> **已归档（2026-09-28）**：本文记录 `setpts=N/FRAME_RATE/TB` 导致推流音画不同步的完整
> 定位过程。日常使用请看 [排障](../troubleshooting.md#bilibili-推流音画不同步)。
> 保留原文仅为遇到同类时间戳/帧率问题时的经验参考。
>
> 适用环境：Linux，ffmpeg 6.1.1，TikTok 直播源 -> Bilibili RTMP 推流
> 涉及文件：`bili/push.sh`、`bili/replay.sh`、`platforms/twitch/twitch.sh`
> 最后更新：2026-09-28

## 现象

- B 站直播间里声音与画面对不上，**偏差随时间持续增大且不会自愈**。
- 推流进程一直活着（systemd `NRestarts=0`，ffmpeg 不退出），日志也无报错，
  所以监控上看不出异常。
- 实际排查发现更严重：**推流约 93 秒后画面完全停住，只剩音频继续播**。
  当时该推流已持续运行 2 小时 52 分。

## 根因

问题出在 `bili/push.sh` 的一行：

```bash
-vf "setpts=N/FRAME_RATE/TB" -r 30
```

这个表达式用**滤镜的帧计数器 `N`** 和**容器里声明的 `r_frame_rate`** 重新生成视频
时间戳，而不是沿用源流的真实时间轴。由此引出两个叠加的故障。

### 机制一：声明帧率与真实帧率不符，video 时间轴被压缩

TikTok 源是真正的可变帧率（VFR），而容器里的 `r_frame_rate` / `avg_frame_rate`
并不反映真实送帧率。实测一条 240 秒的源流：

| 时段 | 真实帧率 | 该窗口内 `setpts` 误差 |
|------|---------|----------------------|
| 0–80 s | 25.00 fps | 0 ms |
| 80–100 s | 21.65 fps | −2680 ms |
| 100–240 s | 15.00 fps | −8000 ms（每 20 秒） |

全程 4535 帧 / 240.1 秒 = **18.89 fps 真实**，而 `r_frame_rate` 全程写 `25`。
`setpts` 按 25 打戳，就把 240 秒的真实视频压进 `4535/25 = 181.4` 秒，
**直接丢掉 58.7 秒**。

### 机制二：滤镜图重新初始化导致时间轴倒卷（致命）

`t ≈ 93.4 s` 处（正是源流降帧率、重起 GOP 的位置），H.264 流出现不连续，
ffmpeg 重新初始化滤镜图，**`N` 归零**。由于时间戳完全由 `N` 推出，
视频时间戳**当场从 93.40 s 倒回 0**，而音频继续在 93.46 s 往前走。
这次倒卷永久无法恢复——`N` 重新计数，视频被压到音频的时间轴后面。

### 为什么音频侧救不回来

音频侧的 `aresample=async=1` 只对**音频自己的**时间戳做补偿，
ffmpeg 内部**没有任何跨流同步机制**。两条时间轴一旦分开，就只会越差越远。
`aresample` 不是同步器，不能修正这个问题。

## 证据

### 1. 源流本身是同步的

拉取 240 秒源流统计：视频 4535 帧、跨度 240.117 s；音频 5626 包、跨度 239.959 s。
两条流本身就对齐，**不是源的问题**。

### 2. 推流产物的时间轴终点

对比推流输出里两条流的 `pts_time` 终点，差值就是当前音画偏差：

```bash
ffprobe -v error -select_streams v -show_entries packet=pts_time -of csv=p=0 out.flv | tail -1
ffprobe -v error -select_streams a -show_entries packet=pts_time -of csv=p=0 out.flv | tail -1
```

| 推流参数 | 视频终点 | 音频终点 | 偏差 |
|---------|---------|---------|------|
| 修复前 | 93.42 s | 240.04 s | **−146.6 s** |
| 修复后 | 240.29 s | 240.04 s | +0.25 s |

### 3. 两条时钟的进度差随时间发散

在多个时间点比较「视频进度百分比」与「音频进度百分比」：

```
修复前   30s:+19.60%  60s:+39.22%  90s:+58.84%   (之后视频停住)
修复后   30s:-0.02%   60s:-0.03%  ...  235s:-0.10%  (全程锁定)
```

修复后的 −0.02% ~ −0.10% 就是源流自身的尾部误差（源为 −0.126%），
即修复是**忠实还原**，没有引入新偏差。

### 4. 画面内容本身没错

逐时间点比对源画面与推流画面的灰度，修复前后都完全匹配。
说明**问题纯粹在时间轴，不在数据**——这也是定位时能把范围缩到时间戳的关键一步。

## 解决方案

核心思路：让视频时间戳**跟随源流的真实时间轴**，而不是用帧计数器重造一个。

### 主修复

用 `fps` 滤镜替代 `setpts`。`fps` 按**输入真实时间戳**做 CFR 转换
（丢帧/补帧到目标帧率），保留真实时长；滤镜图重新初始化也不会回卷。

```diff
-        -vf "setpts=N/FRAME_RATE/TB" -r 30 \
+        -vf "fps=30" \
```

### 配套修正

```diff
-        -fflags +genpts+igndts+discardcorrupt \
+        -fflags +discardcorrupt \
-        -af "aresample=async=1" \
+        -af "aresample=async=1:first_pts=0" \
```

- 去掉输入侧的 `igndts`：FLV 容器没有 PTS，`igndts` 会让 B 帧的 PTS 等于 DTS
  而打乱显示顺序，而 `fps` 滤镜依赖真实时间戳。实测去掉与否对偏差无影响，
  但保留它会干扰 `fps` 的输入。
- 输出音频加 `first_pts=0`：把音频起点也钉到 0，与视频起点对齐
  （`platforms/twitch/twitch.sh` 原本就这么写）。

### 三个脚本的同一处修正

`setpts=N/FRAME_RATE/TB` 这个模式在本仓库出现三处，全部修正：

| 文件 | 修正前 | 修正后 |
|------|-------|-------|
| `bili/push.sh` | `setpts=N/FRAME_RATE/TB` + `-r 30` | `fps=30` |
| `bili/replay.sh` | `setpts=N/FRAME_RATE/TB` + `-r 25` | `fps=25` |
| `platforms/twitch/twitch.sh` | `fps=30,setpts=N/30/TB` + `-r 30` | `fps=30` |

`bili/soop.sh` 没有视频滤镜，时间戳原样透传，不受此缺陷影响，未改动。
`archive/yt.sh` 已封存，保持原样。

## 验证

### 离线对照实验（240 秒真实源流）

```
修复前  v:[0.021.. 93.421]  a:[0.000..240.042]   DRIFT = -146.6 s
修复后  v:[0.021..240.288]  a:[0.000..240.042]   DRIFT =   +0.25 s
```

### ground-truth 校验（合成源，闪光与 1 kHz 蜂鸣严格同时刻）

用 `geq` 生成每秒一帧白闪的画面、`aevalsrc` 生成同一时刻的 1 kHz 蜂鸣，
再用 `signalstats` 取亮度峰值时刻与音频包络做互相关：

| 对象 | 偏移 | 漂移 |
|------|------|------|
| 合成源本身 | +1 ms | 0 ms/s |
| 修复前参数 | −19 ms | 0 ms/s |
| 修复后参数 | **+14 ms** | 0 ms/s |

在**格式规整的 CFR 源**上，修复前后都不漂移——说明差别只在 VFR 与断流场景。
真实推流里源是 16 fps 声明 / 15 tbr 的重度 VFR，旧参数错得更离谱。

### `replay.sh` 的分段边界

混合帧率播放列表（分段 A 真 25 fps、分段 B 真 15 fps，各自单独都同步）：

```
修复前  21 flashes vs 20 beeps, 偏移 -2000 ms, video_end=16.02s vs audio 20.06s  →  -4.0 s
修复后  20 flashes vs 20 beeps, 偏移   +28 ms, video_end=20.10s vs audio 20.06s  →  +0.04 s
```

### 生产推流实测

重启后持续观察，跨过 93 秒故障点、经历多次 GOP 边界：

- **时间戳回退/停滞 0 次**（1189 条 progress 采样，覆盖 611.98 s 输出）
- 帧数增量 / 时间增量 = 18351 / 611.66 s = **30.002 fps**（严格 30 fps CFR）
- 输出时间轴与墙钟同步比 **1.0000×**（451 s 墙钟对应 450.98 s 输出）
- 本次运行 ffmpeg 错误数：0，`NRestarts=0`

### 一个容易误读的现象

ffmpeg progress 里的 `frame=`（送进编码器的帧计数）与 `time*30` 会**恒定差
7~10 帧**（约 0.23~0.33 s）：

```
采样 16 个，差值序列：9 8 9 9 8 7 9 9 8 10 9 8 7 8 10 9
```

这个差值**全程恒定、不增长**，是 progress 的计数口径差异，不是音画偏差。
判据应当是「差值是否随时间增长」，而不是「差值是否等于 0」。
真正的音画偏差要用两条流的时间轴终点差来量（见上）。

## 经验教训

1. **`-r` 和 `setpts=N/FRAME_RATE/TB` 不是"修时间戳"，是"重造时间戳"。**
   直播源是 VFR 时这两者都会破坏同步。要规整帧率用 `fps` 滤镜。
2. **滤镜的 `N` 在滤镜图重建时会归零。** 任何以 `N` 为基准的时间戳表达式
   都不能用于长时直播推流。
3. **ffmpeg 没有跨流同步机制。** 音画对齐只能靠「两条流都沿用源的真实时间轴」，
   不能指望 `aresample` 之类去修另一条流。
4. **"进程还活着"不等于"推流正常"。** 故障版本 ffmpeg 一直不退出、
   日志无报错、画面却早已停播。推流健康度应当看**输出时间轴是否随墙钟推进**，
   而不是看进程和退出码。
5. **先确认源本身同步，再怀疑管线。** 本次源流自检一致，才把范围收敛到推流参数。
6. 用**时间轴终点差**做量化判据，比肉眼看播放感受精确得多，也便于写回归对照。

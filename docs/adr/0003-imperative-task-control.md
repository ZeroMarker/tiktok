# ADR 0003：任务期望状态用命令式（请求驱动），不做文件对账

- 状态：已采纳（命令式）；备选方案（声明式对账）记录在案、暂不采纳
- 日期：2026-10-19
- 范围：`webui/`（recorderd 与 WebUI 对录制任务的控制）
- 相关：[ADR 0002](0002-recorderd-split.md)（引擎与 UI 拆成两个进程）

## 背景

一个录制任务只有三种"期望"：**运行 / 暂停 / 不存在**；此外还有一堆**无法从文件推导的运行态**
（是否在直播、是否正在录、`phase=detecting|recording`、是否在退避重启、`restarts` 计数）。
`state/tasks.json` 保存的是期望与启动参数，运行态只存在于 recorderd 的内存里。

于是有两种可能的控制模型：

- **A 命令式（现状）**：请求 → 立即动作。`tasks.json` 是**记录**（期望状态的持久化副本）+
  recorderd 启动时的恢复依据。代码：`POST /start|/pause|/resume|/restart|/delete-task`
  → `jobs.*` → `Recorder.start/stop/restart`。
- **B 声明式**：文件即期望。watcher（inotify/mtime 轮询）或定时器读 `tasks.json`，
  与 `recorder.status()` 做 diff，然后收敛（该起的起、该停的停）。也就是把 recorderd
  写成一个小 reconciler。

## 对比

| 维度 | A 命令式（现状） | B 声明式（文件 + 协调循环） |
| --- | --- | --- |
| 真相来源 | **内存是运行真相**，文件是记录 | **文件是期望真相**，内存是实现 |
| 触发者 | 请求（控制面 socket / SIGTERM） | 文件变更 → diff → 收敛 |
| 手改文件 | 无效（仅启动恢复时读），**安全** | 立即生效，**强大但危险** |
| 写入者 | 单一写者（只有 recorderd 写） | 天然多写者 → 需文件锁或 CAS，否则丢更新 |
| 崩溃语义 | 只对账启动时那一次快照；运行期"意图"丢失 | 任何时刻重启都重新对账，**最终收敛** |
| 部分失败 | 请求失败即失败，调用方决定重试 | reconciler 自动重试/退避，天然自愈 |
| 排障 | 因果链短：一次请求一条动作 | 需归因到"期望 vs 实际的 diff" |
| 额外件 | 锁（`_CATALOG_LOCK`）+ 原子写（tmp+replace，已有） | watcher、diff/防抖/退避、冲突策略、"正在编辑"的文件 |
| 代码量级 | `jobs.py` 约 230 行 | 估计 +150~250 行 + 一倍边界测试 |
| 对运行态的要求 | 无 | 要求"实际状态"可观测（我们有 `recorder.status()`） |
| 适用条件 | 期望状态少、变更低频、单一入口 | 期望状态多/多变、多写入者、需要不停机自愈的大规模编排 |

## 决策

**采用 A（命令式）。** 理由：

1. **期望只有三态、变更极低频。** 线上证据：`state/tasks.json` 的 mtime 停在 10-17 17:41，
   而 45 个任务一直在跑——"期望"几十小时没变过。声明式的主要收益（持续对账）在这种频率下
   几乎不产生价值。
2. **运行态无法从文件推导。** `live` 来自引擎相位 + ffmpeg 是否存活，`phase` 是内存事实；
   声明式只能管"这个引擎该不该存在"，管不了"主播此刻是否在播"。
3. **启动时对账已覆盖声明式的大部分价值。** `restore_jobs()` 就是"启动时对账一次"；剩下的
   增量是"运行期意图不丢"，而我们的运行期意图全部来自 UI 请求（失败会 toast、可重试）。
4. **单一写者已经成立**，声明式会主动引入"多写者 + 写冲突"这一类新故障，换来的能力当前用不上。

历史参照：本仓库**做过一次声明式**——旧模型把期望放在 systemd 临时单元里（systemd 本身就是
reconciler）。放弃它的原因是成本（每频道一套进程 + 每轮冷启动浏览器，曾 ~247 次/小时、
≈0.5 核），**不是协调模型本身有问题**，所以那次迁移不能用来否定声明式。

## 后果（运维必须知道）

**任务目录不是实时接口。** 手改 `state/tasks.json` 的行为（已由单元测试钉住）：

| 你对文件做的事 | 实际后果 |
| --- | --- |
| 把运行中的任务改成 `paused:true` | **引擎照跑**，列表也仍显示运行中；只有下次 recorderd 启动（`restore_jobs`）才按 `paused` 处理 → "下次启动才生效" |
| 手删一条 | 不停引擎；下次启动不再恢复它 |
| 手加一条 | **不启动**任何引擎 |
| 改 `cookies.txt` | 不影响在跑的引擎（Cookie 在 `build_engine()` 时读一次快照） |
| 删录像目录 | 不停录制：引擎的 `_watch_dir` 在下个分段前重建目录 |
| 清空 `state/` | 当前录制照跑，但**下次 recorderd 重启一条任务都不恢复** |

要立即生效只有一条路：走控制面（WebUI 或
`curl --unix-socket state/run/recorderd.sock -X POST -d '{"unit":"…"}' http://localhost/pause`）。

另外两个已知边界：

- **崩溃恢复只到"启动时快照"**：运行期未落盘的意图（比如"刚点了暂停但还没写盘"）会丢；
  UI 侧表现为操作失败可重试。
- **文件损坏按空目录处理**（`_load_catalog()`），意味着损坏/被清空时下次重启会丢全部任务记录；
  计划加 `.bak` 兜底（见 [TODO](../../TODO.md)）。

## 被考虑但未采纳

1. **完整 reconciler**：收益（运行期自愈、支持绕过 UI 改文件）在本项目的规模与变更频率下很小，
   代价是引入多写者冲突与"编辑中的文件立即生效"这两类新风险。不做。
2. **轻量告警（只记录外部改动，不动作）**：成本低（约 30 行），能把"静默不一致"变可见。
   暂缓，在 [TODO](../../TODO.md) 跟踪。
3. **`tasks.json` 版本号 / CAS**：只有在真的出现第二个写入者时才需要。暂不做。

## 什么情况下会重新评估

- 需要**多写入者编排**（别的服务/脚本也来声明任务）；
- 任务数量或变更频率上量级（例如自动按开播表批量增删任务）；
- 需要"收敛式"运维（期望状态由外部系统持续下发）。

任何一条成立时，先打破"单一写者"这条前提，其余设计再跟着调整。

## 证据（代码位置）

- `_load_catalog()` 的全部调用点都在请求处理或启动/停止信号里：`jobs.py` 的
  `list_jobs`（80，**仅展示 paused 条目**）、`start_job`(117)、`pause_job`(145)、
  `resume_job`(159)、`delete_job`(177)、`job_logs`(198)、`restore_jobs`(213)。
- 全 `webui/*.py` 无 `inotify` / `watchdog` / `st_mtime` 轮询 / `threading.Timer` 重读。
- `list_jobs()` 运行态优先：目录条目若 `unit in seen` 直接跳过（`jobs.py:79`）。
- `Recorder._run` 里引擎即使正常返回也按"引擎意外退出，自动重启中"处理（`recorder.py:162`）——
  不存在"引擎自己决定停"的路径。
- 单元测试：`tests/test_webui.py::TaskPauseResumeDeleteTest::test_catalog_edits_do_not_control_running_tasks`。
